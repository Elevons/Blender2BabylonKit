02 — Runtime Basics: loop, objects, and Babylon hooks

Subsystem diagram: runtime-loop.html · Code traces: runtime loop · lifecycle · load

Behavior authors: this is usually your first engine chapter. It explains what runs when and how the kit hooks into Babylon.js. Skim 01 — Architecture first only if you need the two-file export model (glb + manifest).

App vs kit

Your game app (e.g. game/src/main.ts) owns the level lifecycle — normally through a LevelDirector, which creates the Babylon Engine, a fresh Scene per load, and the browser render loop. The kit (b2bkit) owns loading a level into that scene. It also drives gameplay scripts.

LayerTypical ownerRole

EngineDirector (or app)WebGL/WebGPU context, runRenderLoop, getDeltaTime()

LevelLoader itself never calls engine.runRenderLoop — the render loop belongs to the app layer. LevelDirector starts it for you; if you bootstrap manually, you must call it yourself or OnUpdate never runs.

App bootstrap (once, at startup)

Recommended main.ts (see game/src/main.ts): construct a LevelDirector with your canvas + BehaviorRegistry, then await director.Load(manifestUrl). The director fetches the manifest, creates the engine (honouring Large World Rendering), enables Havok, loads the level, and starts the render loop. Per-load app hooks (fallback camera, logging) go in onLoaded. Behaviors can then soft-restart via this.session.Restart().

Manual (low-level) order, for custom harnesses that drive their own frame loop:

  1. Fetch manifest (optional but required for large-world rendering) — FetchAndValidateManifest then CreateLevelEngine(canvas, antialias, manifest) from core/bootstrap.ts when the Blender scene enables Large World Rendering.
  2. const scene = new Scene(engine)
  3. await EnableHavokPhysics(scene, …) — must run before Load. It registers Havok on the Babylon scene.
  4. Register behaviors (BehaviorRegistry + AutoRegisterBehaviors).
  5. const level = await loader.Load(manifestUrl, manifest) — async. It builds everything and calls level.Begin() inside FinalizeLevel (see 04 — Load Pipeline).
  6. engine.runRenderLoop(() => scene.render()) — starts the per-frame loop.

On the manual path there is no LevelDirector, so this.session on behaviors is a warn-and-no-op stub (pass your own LevelSession via LevelLoaderOptions.session to change that). Debug keys (C/I), fallback cameras, and resize handlers are app concerns. See 09 — Workflow.

Load time vs run time

PhaseWhenWhat happens
LoadLevelLoader.Load() until it returnsAppend glb, build entities, ApplyEntityComponents (the component registry), InstantiateScripts (no lifecycle hooks yet), second pass for entity refs, FinalizeLevel, then Begin() → every OnStart once, late rendering + post, then NotifyPostReady() → every OnPostReady once.
RunEvery frame after runRenderLoopscene.render() → Babylon observables → Level.RunFrame → every OnUpdate.

OnStart is not called from the render loop. It runs once at the end of load (before post). OnPostReady runs once immediately after post attach. Physics bodies, triggers, and constraints exist before OnStart runs.

The frame loop (how OnUpdate hooks into Babylon)

Each browser frame, the app calls scene.render(). Babylon runs scene.animate() first (animations + Havok physics, including any fixed substeps). Then it fires onBeforeRenderObservable — where the kit ticks GameClock, interpolates dynamic-body visuals, and runs Level.RunFrame. Then it draws.

Key facts:

  • deltaSeconds passed to OnUpdate comes from the level's GameClock (core/GameClock.ts): the raw getDeltaTime() / 1000 is clamped to maxFrameDeltaSeconds (0.1 s, tab-switch hitch guard) and multiplied by timeScale. Behaviors read the clock as this.time.
  • OnUpdate runs once per scene.render(), on onBeforeRenderObservable — after that frame's Havok step(s) and before the GPU draw. OnFixedUpdate runs earlier, once per physics step on onBeforePhysicsObservable.
  • Particle empty-emitter tracking also uses onBeforeRenderObservable with insertFirst=true. It runs before RunFrame (subsystems/particles.ts).
  • MSDF text draws on onAfterRenderObservable. It runs after the main pass (ui/msdfText.ts).

The observer first ticks level.time (GameClock.Tick — clamp, scale, sync scene.animationTimeScale, particle updateSpeeds, and the Havok timestep for the next frame), then applies visual interpolation for dynamic bodies under fixed stepping, then inside RunFrame order is fixed:

  1. InputManager.Process() — poll gamepad, evaluate actions, fire callbacks
  2. Every behavior's OnUpdate(deltaSeconds) (entity iteration order unspecified)
  3. Registered Level.AddUpdater callbacks (offset/follow cameras)
  4. InputManager.EndFrame() — so WasPressedThisFrame edges last exactly one frame

Time scale: this.time.timeScale = 0 freezes gameplay (behavior deltas, scene animations, particles, physics) while rendering and input keep running. Wall-clock timers — pause menus, slow-motion ramps that write timeScale — advance by this.time.unscaledDeltaSeconds instead. See API Guide — GameClock.

Fixed stepping: by default physics advances by each frame's scaled delta (variable step), so simulation quality varies with frame rate. When the app sets level.time.fixedDeltaSeconds (e.g. 1/60), the scene accumulates wall time and runs 0..N Havok substeps of exactly that size per frame — identical integration at any FPS. OnFixedUpdate fires once per step in both modes; apply forces there, never read input edges there. Dynamic bodies are visually interpolated between the last two steps (subsystems/physics/interpolation.ts), so they stay smooth on displays faster than the step rate; their node transforms show that visual pose, up to one step behind the sim.

Physics vs OnUpdate

Havok steps after your OnUpdate callbacks for that frame. Practical rules:

  • STATIC bodies — never move. They are colliders only.
  • DYNAMIC — use forces, impulses, or set velocity. Writing node.position every frame fights the solver unless the body is ANIMATED.
  • ANIMATED — drive node transforms in OnUpdate (moving platforms, kinematic characters). See 06 — Physics.

Practical rules for behavior authors

  • Subscribe to Babylon observables in OnStart. Remove them in OnDestroy.
  • Use @exposed entity refs. They resolve before OnStart. Guard null anyway.
  • Do not expect a Level handle on behaviors. Use level.ById from app code or @exposed fields.
  • Component data vs runtime code: TAG/COLLIDER/SCRIPT are manifest components. Only SCRIPT rows become Behavior classes. See trace-components.

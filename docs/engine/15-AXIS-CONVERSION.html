15 — Axis Conversion (Blender Z-up → Babylon Y-up)

Blender uses Z-up (+Z up, +Y forward on objects). Babylon and glTF use Y-up (+Y up, −Z forward in world space). This kit bridges the two. Most confusion comes from not knowing which numbers are already converted and which still live in Blender local space.

See also: 05 — Scripting · 03 — Blender Add-on (export) · 06 — Physics · LLM scripting context · MCP: get_axis_conversion(topic?) · get_scripting_context(section="coordinate-axes")

The rule of thumb

Author as if Blender axes are the object's axes. Model forward along +Y, up along +Z. The export pipeline converts physics/component manifest data to Babylon Y-up. Script logic and mesh transforms stay in Blender local space — do not convert @exposed vector3 vars in the manifest.

Two coordinate frames

Blender (object local)Babylon (world / glTF)
Up+Z+Y
Forward+Y−Z (cameras look down −Z)
Right+X+X
HandednessRight-handedRight-handed

These are not the same frame. Mixing them in one calculation (e.g. adding a Babylon Vector3.Forward() offset to a Blender-local node.position) produces silent 90° errors.

The export formula

Component and physics serializers in blender_addon/export/component_serializers.py convert vectors from Blender to Babylon:

(x, y, z)_Blender  →  (x, z, −y)_Babylon

Related rules in the same module:

  • Extents / size — Y and Z components swap ([sx, sy, sz] → [sx, sz, sy] on colliders).
  • Quaternions — w unchanged; vector part converted with the same axis map ([qx, qy, qz, w] → [qx, qz, −qy, w]).
  • Constraint preset axes — Blender X/Y/Z enum maps to Babylon unit vectors (Y → [0,0,−1], Z → [0,1,0], etc.).

The runtime reads manifest physics values as Babylon space. Do not apply the formula again in behaviors.

Why @exposed vector3 is not converted

_serialize_vars writes list(v.v_val) unchanged. At runtime ApplyExposedVars assigns them with Vector3.FromArray. Behaviors use these values in the same frame as node.position — Blender local space:

  • Rotator — axis: [0, 1, 0] → spin around Blender forward (node.rotate).
  • Patrol — offset: [5, 0, 0] → added to node.position (both local).
  • Waypoints — point list written directly to node.position.

Converting only the manifest var (but not node.position) would mix frames and break these behaviors. For world-space targets, use an @exposed({ type: "entity" }) picker or compute from getAbsolutePosition() — not a raw converted vector3.

Node local space at runtime

glTF export applies the Y-up flip at the scene/root level. Each loaded node's local axes remain Blender's: +X lateral, +Y forward, +Z up. The rest rotation quaternion from Blender is loaded as-is; local rotations in behaviors act in this frame (BoatRocker.ts documents pitch on X and roll on Y in local space).

node.position is parent-local (standard Babylon hierarchy). World position: node.getAbsolutePosition() (Babylon world Y-up).

Behavior APIs that confuse authors

lookAt / setDirection

TransformNode.lookAt(target) calls setDirection, which aligns the node's local +Y axis toward the target — not +Z (despite some Babylon documentation wording).

  • Model arrow tips / forward along Blender +Y.
  • Default space is Space.LOCAL. Works for unparented nodes.
  • When the node has a rotated parent (e.g. HUD mesh parented to the camera), LOCAL space mis-computes direction — the mesh appears not to rotate. Pass Space.WORLD:
import { Space } from "@babylonjs/core";

this.arrow.lookAt(this.target.node.getAbsolutePosition(), 0, 0, 0, Space.WORLD);

Reference: apps/playground/src/behaviors/ObjectiveArrow.ts.

Viewport previews

Blender viewport overlays (viewport/collider_preview.py, cog_preview.py, probe_preview.py) draw raw Blender values. After export conversion, runtime physics bodies match what you authored — the cyan collider wire and amber CoM cross use the same numbers you typed, then export maps them to Havok space.

Prefabs — linked .blend files

Reuse authored content across levels by treating each separate .blend file as a prefab: link it into your level scene, then apply Blender library overrides on the instances you want to customize.

See also: data-model · export · GUID trace · 03 — Blender Add-on · 09 — Workflow

What counts as a prefab

A prefab is a library .blend you link into the level you are exporting — not an app-level or runtime concept. Typical layout:

  • Prefab source — e.g. Small Rover.blend with meshes, empties, components, and GUIDs authored once.
  • Level scene — e.g. Train Scene.blend that links the rover (and other prefabs), places instances in the world, and exports to public/levels/….

Linked objects arrive read-only. To move, retarget scripts, or tweak colliders on one copy without changing the library file, you need a library override on that instance (or on a parent collection that contains it).

Authoring workflow

  1. Build the prefab in its own .blend — components on objects, behaviors wired, colliders previewed, GUIDs assigned where references need them.

  2. Link into the level — File → Link…, or use the link button next to any ENTITY exposed-var picker (runs bjs.link_prefab: pick a .blend, choose a collection, auto library-override, assign the root to the field). The linked hierarchy appears in the level outliner. Children that are parented under the root but not members of the source collection would be left by Blender's override as orphan datablocks (invisible, skipped by export) — the operator links those into the scene automatically; export validation also warns when a referenced object is in no collection. Best practice: make every child (LOD meshes included) a member of the prefab's collection in the library file.

  3. Make a library override — required when linking via File → Link… yourself (select the linked collection or object, then Object → Relations → Make Library Override). The link-prefab button does this automatically. You can override at collection scope so the whole prefab instance is editable as one unit.

  4. Customize the instance — transform, visibility, mesh slots, and Babylon components on the overridden copy. Unchanged fields keep tracking the library; overridden fields are stored on the level .blend.

  5. Export the level as usual — linked + overridden objects in the active scene are flattened into the level .glb and .scene.json like any other renderable object.

Editing components on overrides

Component data lives on Object.bjs_components (and nested PropertyGroups for @exposed fields, trigger rows, particle texture slots, etc.). Blender only allows overrides on RNA properties explicitly marked library-overridable.

The add-on registers that entire chain via core/props.py wrappers around bpy.props — every scalar field gets LIBRARY_OVERRIDABLE; collections (the component stack, exposed-var lists, trigger events, …) also get USE_INSERTION so you can add or remove rows on an instance.

After updating the add-on, disable and re-enable the extension (or restart Blender) so the flags register. Overrides created before that update may need to be re-applied or touched once so Blender records the new override operations.

Use the pin button in Babylon Object → Components when editing entity lists or picking trigger targets across a prefab hierarchy — the inspector stays on the prefab root while you change the viewport selection.

Sync Variables on an override

An override cannot delete its linked base rows — a collection with USE_INSERTION only lets you add or remove rows you inserted locally. So re-reading the .ts on a linked instance could never drop an @exposed var the script does not declare; the stale row would linger.

To avoid that, Sync Variables treats the prefab source as the structural authority for overrides. When the object is a library override, operators/scripts.py resolves the read-only source object through override_library.reference, finds the matching SCRIPT component, and rebuilds field descriptors from its exposed_vars (build_fields_from_component) instead of parsing the file. The source is never modified — only read.

Because an override's linked rows are the source's rows, the only vars that can be dead on the instance are stray local insertions (from a bad sync or enum-reindex corruption). Blender refuses remove() on an override collection (TypeError: … not supported for this collection), so those strays can't be deleted one at a time — but clear() is allowed and drops only the locally-inserted rows while keeping the linked base rows. The override sync therefore clear()s the collection (removing the strays), then reconciles the surviving linked rows in place against the source. Nothing is re-added — the linked rows already match by name — so this avoids the duplication a clear()+rebuild would cause (a common pitfall: clear() keeps the linked rows, then re-adding them stacks duplicates).

The result: syncing cleans up strays, keeps per-instance value overrides, and leaves the instance a faithful mirror of the prefab. @exposed names that exist in the script but not yet on the prefab source are added as temporary local rows on the override (prefab source names take precedence for type and default). After you sync and save the prefab library, reload the library in the level and sync again — the temporary local row is cleared and the field lives on the linked base row. To drop a variable from linked instances, edit the script and run Sync Variables in the prefab file (overrides cannot remove linked base rows).

Local component rows need PropertyGroup names

A library override does not store a full copy of bjs_components. It stores a diff of insert ops (INSERT_AFTER) against the linked source. Blender keys those ops by each row's PropertyGroup name.

Authoring rules

  1. Name the shared stack in the prefab .blend. On local objects, add / paste / duplicate / move run ensure_component_collection_names so legacy unnamed rows get stable hex names. Those names travel with the link and give level inserts a clear INSERT_AFTER anchor.

  2. New local inserts on a level override call assign_component_row_name (add / paste / duplicate). Each new row gets its own hex name and survives save and library reload.

  3. Do not rename linked base rows on an override. A new local name on a linked row makes Blender re-diff it as an INSERT_AFTER. On reload you get that insert and the original linked row — duplicated scripts, colliders, and rigidbodies. The add-on skips ensure_component_collection_names on library overrides for that reason.

If the library rows stay unnamed, Blender falls back to fragile index or empty-name insert ops. The first one or two local inserts can stick. Later unnamed inserts often vanish on reload. A mix of unnamed library rows and one named insert can also reshuffle order on save.

Put the default component stack in the prefab library when every instance needs it. Use level-side inserts only for instance-only extras.

Repair Override Components

Delete cannot remove linked prefab rows. It also cannot remove stuck hybrids — renamed linked-base rows that Blender recorded as inserts. clear() does not drop those hybrids either.

When the stack looks doubled (export warns when an override has at least twice as many rows as the prefab), open the component ▾ menu and choose Repair Override Components (bjs.repair_override_components / RepairOverrideComponentStack in components/clipboard.py):

  1. Stages true instance-only extras (named surplus rows the prefab does not own, or a second copy of one it does).
  2. Calls override_library.reset() to restore the prefab component stack.
  3. Writes location, rotation, scale, parent, and visibility back so the instance keeps its level pose.
  4. Re-adds the staged extras with fresh row names.

After repair, re-check script entity references if you had overridden them on linked SCRIPT rows. Parent and transform overrides stay.

Instance @exposed settings reset on reload

The add-on does not clear script values on file load. When an instance setting (for example Swap Steering) snaps back after reload, Blender dropped the library-override REPLACE op.

That happens when the prefab's component rows have empty PropertyGroup names and the level override also has local component inserts. Override paths then use indices like bjs_components[3].exposed_vars["swapSteering"].b_val. Inserts reshuffle those indices on reload, and the REPLACE ops for floats/bools are lost.

  1. Open the prefab .blend (for example Engine Rover.blend).
  2. Component ▾ menu → Ensure Component Row Names (or add/move any component once).
  3. Save the prefab. In the level, reload the library (or reopen the level).

Entity pointer overrides often still stick in the broken case. Floats and bools are the ones that vanish. Adding a local component on an override warns when the prefab rows are still unnamed.

GUIDs and multiple instances

Entity identity is obj["bjs_id"] (see GUID trace). Linked copies initially share the library GUIDs. That is fine when one instance is in the level; for several instances of the same prefab, each object that becomes its own runtime entity needs a unique id.

On export, _dedupe_entity_ids (export/level.py) detects duplicate bjs_id values among scene objects and re-issues fresh GUIDs on the later duplicates. You can also assign overrides per instance ahead of time:

  • Assign GUID in the Babylon Object panel on the overridden object.
  • Or override the bjs_id custom property in Blender’s Object Properties → Custom Properties (separate from RNA components).

Duplicated linked instances often keep RNA entity pointers aimed at the first linked copy (e.g. Small Rover.003 still constraining to Engine Rover instead of the paired engine instance). Export does not guess or remap — it serializes the object you picked and that object's bjs_id. Re-pick cross-prefab targets on the level override (camera → vehicle, trailer → engine, constraint partners across prefabs). Validation warns when a pointer's instance suffix does not match the owner's.

References inside one prefab (wheels, arms, body self-ref) should point at objects inside that prefab hierarchy in the prefab source file. When you duplicate the prefab in the level, stale same-prefab pointers also need a level override re-pick — or fix them once in the prefab source before linking.

Live Link and prefabs

Live Link re-exports the active level .blend. Edit prefab sources freely, but remember:

  • Saving the library file does not run Live Link on the level unless that file also has Live Link enabled.
  • Saving the level re-exports the merged result — linked data is resolved at export time from whatever the override references.

Iterating on a prefab: save the library → switch to the level → save (or export once) to push changes through.

Runtime

Export produces a flat level (level.glb + scene.json) — there is no separate prefab asset format in v1. Linked instances become ordinary entities (distinct GUIDs after export dedupe). When instances share mesh data in the glb, later copies may load as Babylon InstancedMesh; colliders and reflection probes still resolve geometry via core/meshOwnership.ts.

Runtime spawn (Level.Spawn / this.spawner.Spawn)

The engine can duplicate any loaded entity subtree at runtime with fresh GUIDs and the full component pipeline (physics, scripts, constraints, remapped internal refs). The template is whichever entity is already in the level — a linked/appended collection root or an in-scene hierarchy. Behaviors use the injected this.spawner.Spawn(template, options) surface (they never receive a Level handle); app code can call level.Spawn directly.

  • Parenting — SpawnOptions.parent: omit to match the template root's parent; pass an Entity to parent under it (spawn transform is local to that entity); pass null for scene root (spawn transform is world space — use when clones must not follow a moving template parent, e.g. animalSpawner.ts).
  • Spawn transform — position, rotationQuaternion, and scaling are applied on the hidden clone before meshes are revealed (loader/prefabSpawn/clone.ts → ApplySpawnTransform). Pass the final root transform in SpawnOptions so nothing flashes at the template pose or scale during the async component/finalize pipeline. For grow-in spawns, pass scaling: Vector3.Zero() up front and lerp to the template's authored scale after spawn (see animalSpawner.ts).
  • Template hide (default) — Spawn hides the template and tears down its live components at the start of the call (before the clone is built). Pass keepTemplate: true to leave the source visible. Mark spawn-source fields with @exposed({ spawnTemplate: true }) (entity or entity list) to hide referenced templates at level load — before any OnStart — for deferred spawners such as animalSpawner.ts. Omit spawnTemplate when the template must stay visible until spawn (e.g. populateprefabs.ts with “Keep original prefabs”). HideTemplate hides a template without spawning; repeated hides are no-ops.
  • Prefer STATIC rigidbodies on templates — a hidden DYNAMIC body still simulates until hide runs.
  • Do not node.clone() and copy attachments; that skips physics rebuild and GUID remapping.
  • REFLECTION_PROBE on templates is skipped at spawn (console warning).
  • LOD components spawn correctly when their target meshes live inside the template hierarchy — each instance then clones its own LOD meshes. A target outside the subtree is shared with the template and Babylon rejects reusing it as an LOD level.
  • LOD targets are force-exported as entities (GUIDs assigned pre-glb), but only if they are real scene members: render-disabled objects and orphan override children (in no collection) never export — runtime logs target … not found. LOD target meshes also need unique mesh data: shared glTF meshes import as InstancedMesh, which Babylon LOD rejects (runtime logs only owns instanced meshes).
  • Cameras spawn per instance — typed CAMERA components (ARC / FOLLOW / OFFSET / UNIVERSAL / GEOSPATIAL) are rebuilt with target refs remapped onto the new instance. Spawned cameras are never made active; activate one via scene.activeCamera = handle.cameras[0].
  • Animation — when the template has an animation block in the manifest (autoPlay, Action clip name, loop, speed), spawn clones the skeleton (glTF skins often share one rig), clones and retargets AnimationGroups onto the new hierarchy, resets bind pose, and auto-plays each instance from frame 0 on its own timeline. Hide the template when only clones should animate. Templates with ANIMATOR get a fresh controller per instance that drives those cloned clips.
  • Shadows — spawned meshes register on existing shadow generators as casters and receivers, honoring Blender ray-visibility Shadow (bjs_cast_shadows survives the clone). For multi-spawn loops, pass deferShadowRefresh: true on each Spawn and call FlushSpawnShadowRefresh() once afterward (see populateprefabs.ts). Single spawns and interval spawners register immediately.

Paint-scatter (playground populateprefabs.ts): vertex-paint bright values on a target mesh, leave the color-kind field blank for auto-pick, and use a luminance threshold (~0.5) rather than pure white. When Blender exports “all vertex colors” without wiring the attribute into the material, it invents an all-white COLOR_0 and puts the real paint in COLOR_1. Stock Babylon only loads COLOR_0; the kit’s bjs_extra_vertex_colors extension (registered from LevelLoader) keeps COLOR_1+ on the mesh as getVerticesData("COLOR_1"). Blender attribute names like Color.001 are not glTF kind names.
